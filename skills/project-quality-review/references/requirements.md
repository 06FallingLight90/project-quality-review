# 需求实现度审查清单

实现度审查回答一个问题：项目声称要做的事，代码是否真的做了、做完了。核心不是"有没有代码"，而是"有没有可验证的实现证据"。方向与文档化清单相反：文档化查"文档是否如实描述实现"，本清单查"实现是否兑现声明"。

## 1. 需求声明收集

判定标准：
- 需求来源按优先级：需求/设计文档（docs/、requirements、PRD）→ README 功能描述 → CHANGELOG/roadmap 规划项 → issue/任务系统引用。
- 无任何需求文档是事实，如实标注"无声明需求"，此时仅做 README 级别的功能声称核对，并注明"推断"。
- 从声明中提取两类清单：**功能性**（系统能做什么）与**非功能性**（性能/可用性等指标与约束，含 SLO、合规要求）。

## 2. 功能性实现度

判定标准：
- 逐条声明找实现证据：入口点、路由/handler、核心逻辑、测试。无证据的声明标注"声称有但无实现"。
- 区分完整实现与空壳：TODO、占位、永远返回固定值的桩实现按"部分实现"计，注明位置。
- 部分实现要指出缺口：声明的能力中哪条路径没实现（错误路径、边界、分支）。

## 3. 非功能性实现度

判定标准：
- 声明了量化指标的（响应时间、并发量、错误率），核对是否有对应支撑机制与测试/监控手段；无法核对的标注"推断 + 验证方式"。
- 声明"支持 X"而无量化指标的，用 quality-attributes.md 第 3 节的场景六要素构造核对场景。
- 与外部质量评估联动：效用树场景优先从项目声明的非功能需求提取。

## 4. 反向核对（实现无声明）

判定标准：
- 存在明显功能模块但在任何声明中均未提及 → 可能是夹带、遗留或文档过期，列入文档债而非直接算问题。
- "说了但没实现"与"实现了但没说"大量并存 → 文档与实现双向脱节，作为系统性信号在报告中单列。

## 5. 实现度矩阵输出

- 每条声明一行：`声明（来源） → 状态（已实现 / 部分实现 / 未实现 / 推断）→ 证据位置 → 缺口说明`。
- 无声明需求时输出简化版：仅 README 声称功能核对表。
- 实现度矩阵不改变总体评级口径，但"声称有而无实现"的核心功能按严重度计入问题清单（是否阻塞取决于功能是否核心）。
