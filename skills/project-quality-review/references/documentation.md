# 文档化审查清单

文档审查的核心不是"有没有"，而是"准不准、能不能用"。

## 1. README（根目录）

判定标准：
- 说清三件事：项目是什么、怎么跑起来、目录/模块怎么导航。
- 快速开始步骤可执行：命令真实存在、依赖版本有交代。
- 新鲜度：README 提到的文件、脚本、配置在仓库中真实存在；抽查 2-3 条命令与实际入口比对。
- 功能声称反向核对：README 列出的功能/特性逐条与实现比对（详见 requirements.md）；"声称有但无实现"既是文档问题也是实现度问题，双记。

## 2. 架构文档

判定标准：
- 中大型项目应有架构说明（模块划分、数据流、技术选型理由），缺失即 P1。
- 架构文档要与代码现状比对：描述的模块是否还存在、目录是否对得上。过期架构文档比没有更糟。
- 完整性骨架 W5HH（七问）：Why（为什么做，要解决什么问题）/ What（做什么，功能边界与架构形态）/ When（版本计划或里程碑）/ Who（模块归属与负责方）/ Where（部署运行环境）/ How（技术栈与关键设计）/ How much（规模或成本量级）。中小型项目至少应回答 Why / What / Where / How 四问，缺失项写入报告；早期项目缺 When / How much 不算问题。

## 3. 关键决策记录

判定标准：
- 重大技术选型（数据库、框架、自研组件）有无理由记录（ADR、docs/design 或 README 段落）。
- 无记录不一定是高严重度问题，但"为什么这样做"完全无处可查时应报告。
- ADR 不可复活约束：审查发现与已记录决策（ADR、设计文档结论）冲突时，仅当冲突已造成具体可举证的摩擦才提出，且必须显式标注「与 ADR-xxxx 冲突」并说明为何值得重新开启；不因「教科书式正确」泛泛建议推翻既有决策。

## 4. 代码注释质量

判定标准：
- 公共 API（导出函数、类、接口）有无用途说明；参数含义能否从签名推断。
- 注释与实现是否脱节：注释说 A 代码做 B（改名或改逻辑后忘改注释）。
- 不要求逐行注释；无意义注释（// 获取用户 上方是 getUser）反而扣分。

## 5. 运行与协作文档

判定标准：
- 环境变量、密钥、外部服务依赖有清单；.env.example 存在且与代码实际读取的变量一致。
- 中大型项目应交代贡献规范（如何跑测试、如何提交）。
- CHANGELOG 或等价物存在与否，视项目阶段判断严重度。

## 6. 文档过期的系统性信号

- 大量"文档说有但代码没有" → 文档流程问题，在报告中单列。
- 高频核心模块（核心服务、公共库）完全没有说明性注释或文档。
