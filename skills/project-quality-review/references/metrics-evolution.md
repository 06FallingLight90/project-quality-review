# 架构度量与演化审查清单

度量是客观性最高的评估手段：静态度量不需执行软件，成本低、不依赖运行环境。用 scripts/dependency_metrics.py 获取客观指标，再结合本清单解读。

## 1. 为什么要度量（审查价值）

- 在设计早期发现架构不合理之处，降低开发风险
- 把握整个系统的设计结构与版本更新问题
- 对架构演化程度进行评估和预测
- 度量结果可与外部质量属性变化建立关联（内部结构劣化 → 线上质量劣化）

## 2. 结构度量指标

**依赖类**（由 dependency_metrics.py 计算）：
| 指标 | 含义 | 判读 |
|------|------|------|
| 依赖环 | 模块间循环 import | 任何依赖环都是 P0/P1：环内模块无法独立复用与测试 |
| 扇出（出度） | 模块依赖多少其他模块 | 过高 → 该模块职责过宽或抽象不足 |
| 扇入（入度） | 多少模块依赖该模块 | 过高 → 稳定核心（可接受）或上帝模块（结合内容判断）|
| 模块平均耦合 | 边数/节点数 | 整体趋势比绝对值有意义，多版本对比更佳 |

**解读原则**：指标不直接定罪——高扇入的 utils 若内容内聚是健康稳定核心；高扇入且内容混杂才是问题。必须打开文件确认。

**复杂度类**（结合 mechanical_checks.py）：
- 超大文件分布（≥500 行 warn / ≥1000 行 error）与依赖热点重合 → 复杂度集中区
- 目录深度 >6、单目录文件数 >30 → 结构性可维护性下降

## 3. 架构演化度量

- **演化方式**：静态演化（设计时/运行前，未运行或停机状态）与动态演化（运行中不中断服务：外部请求触发如灰度发布/限流调整，内部策略触发如自动扩容/熔断降级）
- **度量与演化的关系**：对演化前后不同版本的架构做度量，分析质量属性变化，找出**内部结构变化与外部质量属性变化的关联**；归纳多版本变化趋势，总体把握和控制演化过程
- **审查操作**：对有 Git 历史的项目，抽取 2-3 个历史版本跑 dependency_metrics.py 对比：
  - 依赖环数量变化（增加 → 演化失控信号）
  - 热点模块的扇出增长（修改扩散）
  - 超大文件行数增长曲线（腐蚀速率）

## 4. 架构腐蚀（erosion）

- **含义**：实现逐渐偏离预期架构——代码结构与设计文档/意图的偏差持续扩大
- **审查信号**：
  - 分层被穿透（底层 import 上层）
  - 新功能绕过既定模式（同类操作出现第二种实现路径）
  - 文档描述的模块与实际目录对不上
- **预防控制三策略**：
  1. **腐蚀最小化**：变更时主动评估对架构的影响（评审要点）
  2. **腐蚀预防**：架构守护规则（如依赖方向 lint、模块边界测试、import 检查）
  3. **腐蚀修补**：定期度量比对、专项重构
- 报告中若发现腐蚀，按上述三策略给出针对性建议，而非只说"防腐"

## 5. 架构恢复（recovery）

- **含义**：从实现中恢复出软件架构（逆向），用于理解、评估和重建系统
- **审查操作**：当文档缺失/过期时，从代码恢复真实架构（模块划分、依赖图、入口到存储的数据流），并明确标注"这是恢复的现状架构，非设计意图"
- 恢复结果与文档的 diff 本身就是文档债清单

## 6. 基于度量评估的架构重构过程

1. **重构点识别与定位**：用度量指标（依赖环、扇出、超大文件、重复块）定位重构点；按抽象层次、重构粒度、重构需求选择识别方法
2. **重构方案**：针对每个重构点给出目标结构（如"拆分 X 为 A/B，引入接口 I"）
3. **实施与验证**：不改变功能与外部可见性的前提下改造；验证手段 = 度量指标改善 + 测试通过
4. **迭代**：重构 → 再度量 → 再定位，循环直至指标进入合理区间

重构收益口径：提高可读性、可扩展性、可重用性、可维护性。
