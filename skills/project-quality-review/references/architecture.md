# 架构设计审查清单

按此清单审查架构。每条问题必须落到具体文件或模块，并说明判定依据。

## 1. 分层与依赖方向

判定标准：
- 依赖必须单向：上层依赖下层（接口层 → 业务层 → 数据访问层），禁止反向依赖。
- 领域/核心层不得依赖框架、ORM、HTTP 等外部设施细节。
- 跨层调用要有明确通道，禁止业务层直接拼 SQL 或直接操作 HTTP 请求/响应对象。

获取证据：
- 从入口点出发追一条完整调用链，记录每一层 import 了谁。
- 在核心模块中搜索框架类 import（如 domain 包内出现 requests、gorm、express 等设施依赖）。

## 2. 模块边界与耦合

判定标准：
- 模块之间不允许循环依赖。
- 模块对外只暴露稳定接口；其他模块 import 其内部文件（非公开 API）即边界泄漏。
- 警惕上帝模块：被所有模块依赖、什么都装的 common/utils/core。

获取证据：
- 抽取各模块 import 关系，识别依赖环与扇入扇出异常。
- 打开 utils/common 类目录，判断内容是否混杂互不相关的职责。

组件级设计原则（SOLID，逐条按证据判定，不做教条式检查）：
- OCP（开闭）：新增一类行为需要修改核心函数的分支/switch-case 或多处同步改动，而非只新增实现文件，即违反。
- LSP（里氏替换）：子类覆盖后抛 NotImplemented、空实现或弱化前置条件，使用父类型处换成子类即行为出错，即违反。
- DIP（依赖倒置）：高层业务逻辑直接 import 具体实现（具体客户端类、具体 ORM 模型）而非抽象接口，替换实现需改动业务代码，即违反。
- ISP（接口隔离）：接口方法远超使用方实际调用面、实现方被迫实现大量用不到的方法，即胖接口，按「模块对外只暴露稳定接口」的边界泄漏问题报告。

## 3. 一致性与模式

判定标准：
- 同类问题应只有一种解法：并存三种数据库访问写法、两种错误处理模式即不一致。
- 模式使用要有理由。为了模式而模式的嵌套（Factory 里套 Strategy 套 AbstractFactory）与缺失抽象同样扣分。

获取证据：
- 对同一操作（如"创建一条记录并返回"）找 2-3 处实现，比较调用路径是否一致。

## 4. 抽象质量

判定标准：
- 泄漏的抽象：接口方法暴露实现细节（如接口参数里带 SQL 片段）。
- 过早抽象：只有一个实现却强行抽接口且无可预见的替换场景。
- 缺失抽象：同一硬编码逻辑散落多处，改动需多处同步。

## 5. 接口契约质量

契约范围：模块公开 API、类/方法签名、HTTP/RPC 接口、事件/消息 schema、数据库表结构、文件格式、配置项、CLI 参数——一切被调用方长期依赖的跨边界约定都算契约。改实现通常便宜，改契约昂贵；契约质量差是 Shotgun Surgery 与 Dense Structure 的常见成因（判"果"见 code-smells.md 第 9 节，此处判"因"）。

按影响面分级，不做全量严查：对外公开 API、跨模块/跨团队接口、持久化 schema、事件契约严查；模块内部接口适中；私有函数不做契约级设计要求。

判定标准：
- 错误契约：错误码/异常语义可分类、可编程分支处理，调用方无需解析错误消息字符串；同类接口的错误格式一致。
- 参数与返回约定：边界处有输入校验；返回结构稳定；无布尔标志参数、无 Map<String, Object> 式通用参数袋、无 getter/setter 暴露全部内部状态；参数过多应合并为参数对象。
- 语义契约：幂等性、副作用、超时、重试语义、线程安全、生命周期是否声明——有并发或跨进程调用方而未声明即问题。
- 兼容与演进：变更不破坏既有调用方（改字段类型、删参数、改语义均属破坏）；对外契约有无版本策略或弃用标记；schema/事件结构变更是否同步了所有调用方。
- 一致性：同类接口的动词/资源命名、分页、过滤、错误格式统一（如 `get_x` 返回对象而 `fetch_y` 返回 {data: …} 即不一致）。
- 隐式行为：接口内部隐含 IO 或依赖当前时间/随机数而签名不体现，调用方无法从契约推断，即危险信号。

获取证据：
- 抽 2-3 个核心对外接口（HTTP 端点或公共 API），对照真实调用方代码核对错误分支与参数构造方式——调用方需要读实现才知道怎么用，即契约失败。
- 对表结构/事件 schema，用 git 历史查破坏性变更（改类型、删字段）是否与调用方同步修改。
- 命名一致性：列出同类接口的签名并排比较。

## 6. 扩展点与配置

判定标准：
- 会变化的外部依赖（第三方 API 地址、功能开关、业务阈值）应配置化，硬编码即问题。
- 演进成本测试：新增一种同类业务（新支付渠道、新存储后端）需要改多少处？改动点越多架构越差。

## 7. 数据流

判定标准：
- 数据从入口到存储的流转路径应能一句话说清；说不清即边界混乱的信号。
- 贫血模型（纯 getter/setter 数据袋）+ 过胖服务层是常见反模式，按项目规模判断严重度。
