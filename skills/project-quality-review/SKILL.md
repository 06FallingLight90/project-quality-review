# Project Quality Review

对整个代码仓库做只读的软件工程质量体检。目标是发现结构性问题并给出可落地的改进方案，不是逐行 code review。

## 总体原则

- 只报告有证据的问题。每条结论必须附带具体文件与行号或明确的模块关系，禁止"架构不够清晰"这类无证据的空泛评价。
- 区分事实与推断。可从代码直接验证的写为事实；基于经验的推测必须标注"推断"并给出验证方法。
- 改进建议必须可执行。给出目标状态和迁移路径，而不是只说"应该分层"。
- 这是只读分析。除非用户明确要求修复，不修改任何代码。
- 尊重项目语境。脚本语言小工具与后端单体服务的合理结构不同，按项目规模与技术栈校准判定严重度。

## 工作流

### 第一步：项目画像

1. 列出仓库根目录，读取构建与配置文件（package.json、pyproject.toml、pom.xml、go.mod、Cargo.toml、Makefile、CI 配置等），识别语言、框架、构建与测试方式。
2. 识别入口点（main 函数、路由定义、启动脚本）与核心模块划分。
3. 运行两个机械检查脚本获取客观指标（在 skill 目录下执行，目标为项目根目录）：

   ```bash
   python scripts/mechanical_checks.py <项目根目录>     # 超大文件、TODO、深嵌套目录、根文档缺失
   python scripts/dependency_metrics.py <项目根目录>    # 依赖环、扇入扇出、模块级耦合汇总
   ```

   两者均输出 JSON。dependency_metrics 支持 Python 与 JS/TS 的 import 解析；其他语言提示"依赖图未覆盖"并降级为人工追依赖。
4. 开始全面检查前，先通读项目已有的说明性文档（ARCHITECTURE、REQUIREMENTS、README、调用方附带的风险登记表等）作为评估输入线索：声明的需求与设计目标用于实现度和文档维度核对；风险登记表中预判的风险经代码核实已显形的，升级为问题报告条目。
5. 按源码文件数量决定第二步策略：
   - 小型（少于 50 个源文件）：不派子代理，由当前会话携带清单按维度顺序分析。
   - 中大型（50 个及以上）：按维度派发并行子代理。

### 第二步：分维度审查

中大型项目用 Agent 工具（subagent_type=Explore）并行派发。每个代理的 prompt 必须包含：项目根目录、对应清单文件路径、返回格式（问题列表，每条含证据位置、严重度、改进建议），并声明只分析不改代码。维度与清单对应关系：

| 维度 | 清单 |
|------|------|
| 架构设计（分层、边界、模式、抽象） | references/architecture.md |
| 需求实现度（功能/非功能声明 vs 实现证据） | references/requirements.md |
| 质量属性评估（内外部指标、场景、效用树） | references/quality-attributes.md |
| 代码坏味道与技术债（含架构坏味） | references/code-smells.md |
| 目录结构 | references/structure.md |
| 文档化 | references/documentation.md |
| 度量与演化（指标解读、腐蚀、重构） | references/metrics-evolution.md |

- 每个维度独立代理，避免单个代理上下文过载；小型项目则逐份读取清单后顺序分析。
- 机械检查结果（超大文件、TODO 密集区、深嵌套目录、依赖环、扇入扇出热点）作为坏味道、目录与度量维度的输入线索，但必须由代理打开文件确认后才可写成结论。
- 深度评估：用户明确要求深度评估时，按 references/evaluation.md 执行 ATAM/SAAM 轻量流程（质量效用树 + 敏感点/权衡点/风险决策识别）；默认审查至少完成"质量属性场景 × 当前架构支撑度"的简化版。
- 有 Git 历史的项目，用 `git log --name-only` 统计高频共改文件组合，作为 SAAM 场景来源与 Scattered Functionality 证据。

### 第三步：汇总报告

按 assets/report-template.md 的结构输出报告：

1. 项目画像摘要：技术栈、规模、总体健康度评级（A/B/C/D）。
2. 质量属性评估表：内外部质量逐项评级 + 关键场景支撑度（来自 quality-attributes.md）。
3. 需求实现度矩阵：功能/非功能声明 vs 实现证据（来自 requirements.md）；无声明需求时输出 README 级简化核对并标注推断。
4. 分级问题清单：
   - P0 结构性问题——阻碍演进的问题，如循环依赖、上帝类、分层被穿透、核心模块零文档、高风险权衡无意识。
   - P1 维护性问题——显著增加维护成本，如成片重复代码、命名体系混乱、架构文档与实现脱节、无偿还计划的技术债。
   - P2 改进项——局部可优化，如风格不一致、个别超长方法。
5. 每条问题固定格式：证据位置 → 为什么是问题（对照清单中的判定标准）→ 具体改进方案。评估类结论标注方法来源（检查表项 / 场景编号 / 度量指标值）。
6. 技术债清单：按代码债/设计债/测试债/文档债四类归类，每项带优先级与建议偿还时机。
7. Quick wins 清单：投入小、收益大的 3-5 项。
8. 改进路线图：按 P0 → P1 → P2 排序的阶段性建议；若发现架构腐蚀，按"腐蚀最小化 / 预防 / 修补"三策略给专项建议。

评级口径：A 健康可长期演进；B 有债务但可控；C 需要专项治理；D 存在阻碍演进的结构性问题。

## 与其他审查类 skill 的边界

- 用户给出 diff、commit、PR 链接时，那是对变更的审查，不适用本 skill。
- 用户说"审查整个项目""项目质量怎么样""架构有什么问题""帮我做个体检"时使用本 skill。
