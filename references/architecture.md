# 架构设计审查清单

按此清单审查架构。每条问题必须落到具体文件或模块，并说明判定依据。

## 1. 分层与依赖方向

判定标准：
- 依赖必须单向：上层依赖下层（接口层 → 业务层 → 数据访问层），禁止反向依赖。
- 领域/核心层不得依赖框架、ORM、HTTP 等外部设施细节。
- 跨层调用要有明确通道，禁止业务层直接拼 SQL 或直接操作 HTTP 请求/响应对象。

获取证据：
- 从入口点出发追一条完整调用链，记录每一层 import 了谁。
- 在核心模块中搜索框架类 import（如 domain 包内出现 requests、gorm、express 等设施依赖）。

## 2. 模块边界与耦合

判定标准：
- 模块之间不允许循环依赖。
- 模块对外只暴露稳定接口；其他模块 import 其内部文件（非公开 API）即边界泄漏。
- 警惕上帝模块：被所有模块依赖、什么都装的 common/utils/core。

获取证据：
- 抽取各模块 import 关系，识别依赖环与扇入扇出异常。
- 打开 utils/common 类目录，判断内容是否混杂互不相关的职责。

## 3. 一致性与模式

判定标准：
- 同类问题应只有一种解法：并存三种数据库访问写法、两种错误处理模式即不一致。
- 模式使用要有理由。为了模式而模式的嵌套（Factory 里套 Strategy 套 AbstractFactory）与缺失抽象同样扣分。

获取证据：
- 对同一操作（如"创建一条记录并返回"）找 2-3 处实现，比较调用路径是否一致。

## 4. 抽象质量

判定标准：
- 泄漏的抽象：接口方法暴露实现细节（如接口参数里带 SQL 片段）。
- 过早抽象：只有一个实现却强行抽接口且无可预见的替换场景。
- 缺失抽象：同一硬编码逻辑散落多处，改动需多处同步。

## 5. 扩展点与配置

判定标准：
- 会变化的外部依赖（第三方 API 地址、功能开关、业务阈值）应配置化，硬编码即问题。
- 演进成本测试：新增一种同类业务（新支付渠道、新存储后端）需要改多少处？改动点越多架构越差。

## 6. 数据流

判定标准：
- 数据从入口到存储的流转路径应能一句话说清；说不清即边界混乱的信号。
- 贫血模型（纯 getter/setter 数据袋）+ 过胖服务层是常见反模式，按项目规模判断严重度。
